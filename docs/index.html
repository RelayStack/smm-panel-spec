Does this panel actually implement the API?

Every panel speaks the same eight-action API and nobody published it, so every integration guesses. Three of these rows can be proven in the next ten seconds, read-only: no order placed, no balance spent.

The eight API actions, their probe status and latency, and what each returns
Action Status Latency Returns
ready — array of services

Request

GET /api/v1?key=YOUR_KEY&action=services

Response

[
  { "service": "5", "name": "Instagram Followers [15K]", "category": "Instagram",
    "rate": "1.02", "min": "500", "max": "10000", "type": "default", "dripfeed": 1 }
]

An empty array is valid. A JSON object here means the request failed and you were handed an error envelope instead.
ready — balance, currency

Request

GET /api/v1?key=YOUR_KEY&action=balance

Response

{ "status": "success", "balance": "24.56", "currency": "USD" }

The balance arrives as a string on some panels and a number on others. Parse to a decimal; a float loses cents across a thousand orders.
ready — status, charge, remains

Request — single

GET /api/v1?key=YOUR_KEY&action=status&order=32

Response

{ "order": "32", "status": "inprogress", "charge": "1.2600",
  "start_count": "0", "remains": "0" }

Request — several

GET /api/v1?key=YOUR_KEY&action=status&orders=12,2

Response

{ "12": { "order": "12", "status": "processing" },
  "2":  "Incorrect order ID" }

In the multi form a failed order is a bare string, not an object with an error field. This is the shape most clients get wrong. The probe asks for an order id that cannot exist and checks that this envelope comes back at all.
not probed — order id

Request

POST /api/v1
key=YOUR_KEY&action=add&service=5&link=https://instagram.com/p/x&quantity=1000

Response

{ "status": "success", "order": 32 }

Not probed, because it spends money and changes state. Success means the order was accepted and the balance debited — not that anything was delivered. Poll status for that.
v2 only — order history

Request

GET /api/v2?key=YOUR_KEY&action=orders&limit=100&offset=0

Response

{ "status": "success",
  "orders": [ { "order": 32, "service_id": 5, "service": "Instagram Followers",
                "link": "https://...", "quantity": 1000, "charge": "1.02",
                "status": "completed", "created_at": "2026-01-01T00:00:00Z" } ] }

Pagination is not standardised. Treat the result as a page, not as the complete history, and do not infer a total from its length.
v2 only — count cancelled

Request

GET /api/v2?key=YOUR_KEY&action=cancel&orders=12,2

Response

{ "status": "success", "cancel": 1 }

“0” is a valid and common answer: a completed order cannot be cancelled. Treat it as success, not as a failure.
v2 only — refill id

Request

GET /api/v2?key=YOUR_KEY&action=refill&order=32

Response

{ "status": "success", "refill": 7 }

The value is a refill id, not a boolean. Keep it: that is what refill_status takes.
v2 only — refill state

Request

GET /api/v2?key=YOUR_KEY&action=refill_status&refill=7

Response

{ "status": "success", "refill": "Completed" }

The refill value set is not closed either. Tolerate strings you have not seen before.

Three probes are read-only; add, cancel and refill write, so the checker never calls them. The numbers this board shows come from report.json — a captured run against the bundled mock server.

python3 conformance/smmcheck.py --base https://panel.example --key $SMM_KEY

Three conventions break every integration

  1. Business errors are HTTP 200

    {"error": "Incorrect order ID"} is a successful HTTP response. A client that treats 200 as success records orders that were never placed.

  2. Money is a string, except when it is not

    "1.02" and 1.02 appear in the same field across versions and panels. Parse to a decimal, never to a float.

  3. add is not delivery

    A success response means the order was accepted and the balance debited. Delivery is asynchronous, so poll status and expect remains to count down.

Run it

One panel

python3 conformance/smmcheck.py \
  --base https://panel.example \
  --key $SMM_KEY

Exit code 0 only when every probe passes, so it drops into CI unchanged. --json gives the same report machine-readable.

Several panels

python3 conformance/smmcheck.py --batch panels.csv

panel    result         pass  latency
panel-a  compliant       3/3     24ms
panel-b  NOT compliant   1/3      1ms

The file is name,base,key per line — the choosing-a-provider case, and the only mode that compares panels side by side.

In CI

- uses: RelayStack/smm-panel-spec@main
  with:
    base_url: ${{ secrets.PANEL_URL }}
    api_key: ${{ secrets.PANEL_KEY }}

A composite action, read-only, so a nightly run cannot cost anything beyond the requests themselves.

What it does not do

It does not judge delivery quality, price, or whether a panel honours its own refill promise. It checks the format, because the format is what breaks integrations at 2am. Panels diverge inside the spec too — if yours does, that divergence is the most useful thing you can send back.
