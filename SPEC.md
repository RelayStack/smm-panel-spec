# SMM Panel API — specification v2.0

Status: **de-facto**. This document records the API that SMM panels and reseller
tools already implement. It introduces nothing. Where implementations disagree,
the disagreement is noted as such rather than resolved.

The machine-readable form of this document is
[`spec/smm-panel-api.json`](spec/smm-panel-api.json). If the two ever disagree,
the JSON is wrong and you should open an issue.

## 1. Transport

| property | value |
|---|---|
| Methods | `GET` and `POST`, both accepted for every action |
| Encoding | `application/x-www-form-urlencoded` for POST |
| Response | `application/json`, UTF-8 |
| Base URL (v1) | `<panel>/api/v1` |
| Base URL (v2) | `<panel>/api/v2` |
| Versioning | path segment, not header; v1 is a subset of v2 |

Parameters are read from the query string on `GET` and from the body on `POST`.
Implementations that accept both in both places exist; clients should send the
body on POST and must not depend on the server merging the two.

## 2. Authentication

The API key travels as the `key` parameter on **every** request, including
`services`. There is no header-based auth in v1 and clients should not assume one
in v2.

`key` selects the account: the balance charged by `add` and the order history
returned by `orders` belong to the key's owner. A key is therefore a bearer
credential for money — anyone holding it can spend the balance. Keys are
regenerated by the panel, which invalidates the previous value immediately.

## 3. The error convention

Failures are returned as **HTTP 200** with a JSON object whose only meaningful
field is `error`:

```json
{ "error": "Incorrect order ID" }
```

This is the single most common integration bug: a client that treats 200 as
success silently records orders that were never placed. A client MUST check for
the `error` key before reading any other field.

The one exception is rate limiting, which uses a non-200 status:

| HTTP | Body | Meaning |
|---|---|---|
| 200 | `{"error": "..."}` | business error |
| 429 | `{"error": "Too many requests..."}` | rate limit hit; back off |

Observed rate-limit shapes vary between 30 and 60 requests per minute per key;
the value is panel-specific and is not part of the contract.

`error` messages are free text and panels differ in wording. Clients must not
match on the string; they must branch on the presence of the field.

## 4. Value types

| concept | representation |
|---|---|
| money (`rate`, `charge`, `balance`) | string decimal, e.g. `"1.02"`; v2 may use a JSON number |
| counters (`min`, `max`, `quantity`, `remains`, `start_count`) | string or number |
| identifiers (`order`, `service`) | number in responses, string or number in requests |
| status words | lowercase, see §5 |

Clients MUST accept both string and number for every numeric field. A client that
calls `int()` on `remains` will break on the panel that returns `"0"`, and a
client that calls `float()` on `charge` will accumulate rounding errors across a
thousand orders. Parse money as a decimal type.

## 5. Actions

### 5.1 `services` — service catalogue (v1, v2)

No parameters beyond `key` and `action`. Returns a **JSON array**, not an object:

```json
[
  { "service": "5", "name": "Instagram Followers [15K]", "category": "Instagram",
    "rate": "1.02", "min": "500", "max": "10000", "type": "default", "dripfeed": 1 }
]
```

Required fields: `service`, `name`, `category`, `rate`, `min`, `max`, `type`.
`rate` is the price per 1000 units in the panel's account currency. An empty
array is valid for an account with no active services; a JSON object is a
violation and usually means the request failed and returned an `error` envelope.

### 5.2 `add` — place order (v1, v2)

| parameter | required | notes |
|---|---|---|
| `service` | yes | id from `services` |
| `link` | yes | target URL |
| `quantity` | yes | within the service's `min`/`max` |
| `runs` | no | drip-feed only: how many deliveries |
| `interval` | no | drip-feed only: minutes between them |

```json
{ "status": "success", "order": 32 }
```

`order` is a number here and a string elsewhere in the same API. Success means
the order was accepted and the balance debited — **not** that delivery happened
or completed. Delivery is asynchronous; use `status`.

### 5.3 `status` — order status (v1, v2)

Single order:

```json
{ "order": "32", "status": "inprogress", "charge": "1.2600",
  "start_count": "0", "remains": "0" }
```

`remains` is the quantity still to be delivered, not the quantity delivered.
`start_count` is the counter value on the target before delivery began.

Several orders at once, via a comma-separated `orders` parameter:

```json
{ "12": { "order": "12", "status": "processing" },
  "2":  "Incorrect order ID" }
```

Note that in the multi form a failed order maps to a **bare string**, not an
object with an `error` field. Clients must handle both shapes.

The `status` value set is not formally closed. In practice: `pending`,
`inprogress`, `processing`, `completed`, `partial`, `canceled` (also spelled
`cancelled`). Clients MUST tolerate unknown values.

### 5.4 `balance` — account balance (v1, v2)

```json
{ "status": "success", "balance": "24.56", "currency": "USD" }
```

`status` is present on some panels and absent on others. `balance` and
`currency` are required.

### 5.5 `orders` — order history (v2)

Optional `limit`, `offset`, `status`. Returns:

```json
{ "status": "success",
  "orders": [ { "order": 32, "service_id": 5, "service": "Instagram Followers",
                "link": "https://...", "quantity": 1000, "charge": "1.02",
                "status": "completed", "created_at": "2026-01-01T00:00:00Z" } ] }
```

Pagination semantics are not standardised across panels. Treat the result as a
page, not as the complete history, and do not infer a total count from its length.

### 5.6 `cancel` — cancel orders (v2)

`orders` is a comma-separated list. Returns the number actually queued:

```json
{ "status": "success", "cancel": 1 }
```

`0` is a valid and common answer — a `completed` order cannot be cancelled.
Clients must not treat `0` as a failure.

### 5.7 `refill` — request refill (v2)

`order` is a single id. Returns a refill id:

```json
{ "status": "success", "refill": 7 }
```

### 5.8 `refill_status` — refill status (v2)

`refill` is the id from §5.7. Returns its current state:

```json
{ "status": "success", "refill": "Completed" }
```

## 6. What this specification does not cover

- **Currency.** Panels return their own; there is no cross-panel unit.
- **Webhooks.** Some panels notify on completion, with panel-specific payloads
  and signing. Not standardised, so not specified here.
- **Rate limits.** Panel-specific values, documented per panel.
- **Field ordering, whitespace, HTTP headers beyond `Content-Type`.**

## 7. Conformance

`smmcheck.py` implements the read-only subset of this document:

- `services` returns a non-empty array whose items carry the required fields;
- `balance` returns `balance` and `currency`;
- an unknown order id produces an `{"error": ...}` envelope rather than a crash.

Passing means a panel is usable by a generic client. It does not mean delivery
quality is good — that is a different question, measured elsewhere.
